# 性能优化案例：低 GPU 利用率下如何缩短实验墙钟时间

## 现象

单任务训练和扩展评估时，RTX 2060 的 GPU 利用率经常只有约 10%–30%，而 CPU 接近满载。
这不代表 PyTorch 没有使用 GPU：显存、CUDA 前向和反向都存在，但模型较小，CPU 需要完成
NPZ/Parquet 读取、batch 组装、质量特征刷新、确定性污染和大量小场景调度，GPU 经常等待。

## 定位方法

1. 同时观察 GPU utilization、显存、CPU 和单阶段耗时；
2. 确认 checkpoint 和张量确实位于 CUDA；
3. 区分“训练计算慢”与“数据/场景调度慢”；
4. 先跑一个扩展单元做基准，不用模型成绩决定优化；
5. 用合同测试证明优化前后样本、故障和随机语义一致。

## 优化一：场景合批

扩展评估把 8 个场景合并为一次 GPU 批次，减少 Python 循环、主机到显存传输和小 kernel
调度。若 6GB 显存不足则单元失败，不静默修改 batch 或场景语义。

## 优化二：双任务并行

训练和扩展评估分别通过执行 ADR 冻结为最多两个逻辑单元并行。两个 worker 写独立 run
目录，主控制器是登记表唯一写入者。并行决策只使用耗时、GPU/CPU 和显存，不读取性能值。

## 实测结果

扩展评估单任务基准约 90 秒。首个单元完成后，剩余 59 个单元双路并行从 09:11 运行到
10:16，约 65 分钟；按单任务基准估算串行约 88.5 分钟，墙钟时间减少约 26.5%。并行期间
典型显存约 1.5GB/6GB，未发生 OOM；最终 60/60 成功，样本哈希与聚合合同不变。

加速没有接近 2 倍，因为两个任务继续竞争 CPU、内存带宽和数据读取。这恰好验证瓶颈不是
纯 GPU 算力。进一步盲目增加 worker 很可能只放大 CPU 争用。

## 面试表达

“我没有只看 GPU 百分比就改大 batch，而是把流水线拆成数据、污染、传输、前向和写盘阶段。
模型很小，真正瓶颈在 CPU 场景构造。先做单元基准，再通过场景合批和两路并行减少空转，
同时用协议锁保证科研语义不变。最终墙钟缩短约四分之一，60 个单元全部可追溯。”
